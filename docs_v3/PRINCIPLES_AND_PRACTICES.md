# Engineering Principles and Practices (v3)

How the course practices were applied to the v3 change (prompt [P015](../prompts/PROMPT_LOG.md#p015---v3-postgres-backend-grade-card-prerequisite-warnings-man-page)). v2's account is in [docs_v2](../docs_v2/PRINCIPLES_AND_PRACTICES.md).

## 1. Prompt engineering and AI use

**Clarify before building.** The original request was broad: "proper database", "enforce prereqs". Before any code, the AI asked four questions: which database, where completions come from, where to enforce, and how to deliver commits. The answers changed the design. "Enforce" became "warn", grade cards became the completion source, and an admin source became an extension point rather than a feature. Questions and answers are in the log.

**Log first, then build.** The P015 entry (original prompt verbatim, CoSTAR restatement, negative constraints) was committed before any implementation commit. Each later commit message names P015.

**Negative prompts, by origin.** The log separates constraints the developer stated (warn, don't enforce; U/W/I not completed; extensible to admin records; a new version) from those agreed in planning and those added at review. Review added:

- no real grade cards in Git;
- no PDF storage;
- parameterised SQL only;
- no network in unit tests;
- no change to the existing CSV schemas;
- no invented test counts.

**Constraints are enforced, not just written.** Where possible, a negative prompt became an automated check:

| Constraint | Check |
|---|---|
| No real grade cards committed | `validate.mjs` rejects a PDF fixture without the `SYNTHETIC` marker |
| No real secrets in the template | `validate.mjs` rejects a Neon password in `.env.example` |
| Warnings never change the solve | `prerequisiteInputsNeverChangeWhatTheSolverReceives` |
| Portal and CLI agree | Shared golden file, checked by both suites and by CI |
| No destructive migration by accident | `DROP TABLE` requires a reviewed note |

**Treat AI output as untrusted until verified.** Each AI-written module was tested before commit, and five faults were caught this way ([DEBUGGING.md](DEBUGGING.md)). The real grade card was used once, locally, to validate the parser against the real layout (43 of 43 rows). It was never committed or quoted.

**Report limits honestly.** The build sandbox could not reach Maven Central. Rather than claim the Java suite ran, the docs record that the 19 new Java tests ran against stand-ins, and that the Maven total of 71 is for CI to confirm.

## 2. Software design

- **Single responsibility.** In the portal, HTTP handlers, validation, domain rules, storage and the connection are separate modules. Only `_store.js` contains SQL.
- **Defence in depth.** Validation in JS, then constraints in Postgres (FK, CHECK, PK). A bug in one layer cannot store a row the solver would reject.
- **Open for extension.** Completion sources are a registry. Adding admin records needs one entry and one admin action, with no schema or form change.
- **Separation from the solver.** `PrerequisiteData` sits outside `TimetableProblem`, so the solver cannot depend on it.
- **Backward compatibility.** `SlotbookRun` keeps its v2 constructor, the five CSV schemas are unchanged, and the JavaFX app needs no edits, because it uses only APIs whose signatures are unchanged (its compilation is confirmed by CI, since JavaFX could not be downloaded here).
- **Safe errors.** Internal errors return a generic 500; secrets are compared in constant time; TLS is required for remote databases.

## 3. Version control

v3 was built as one commit per verified step on top of v2, each with a descriptive message and the P015 reference:

1. `docs(prompts)`: log P015 before implementation
2. `feat(portal)`: Postgres storage, migrations, tests, CI service
3. `feat(portal)`: grade-card parsing and prerequisite warnings
4. `feat(cli)`: Java prerequisite warnings, golden file, parity fix
5. `docs`: docs_v3, man page, manual, test plan
6. `docs(prompts)`: P015 review and acceptance

Each commit leaves the test suites passing. A reviewer can check out any step and run it.

## 4. Testing

- **Pyramid.** Pure unit tests (validation, parser, checker) are fast and numerous. Store tests run on an in-memory Postgres. HTTP contract tests call the real handlers. A few integration tests cover what only real Postgres can show (rollback, concurrency).
- **Regression tests for every fault found**, named after the behaviour, not the bug.
- **Cross-implementation contract.** One golden file, three checks (JUnit, Node, CI diff of the real CLI).
- **Test data.** Synthetic, generated by a committed script, with the cases that matter: U, W, I, a retake, a damaged row, a text-less PDF.
- **All tests listed** in [TEST_PLAN.md](TEST_PLAN.md) with what each verifies.

## 5. Documentation

- `slotbook(1)` man page with NAME, SYNOPSIS, DESCRIPTION, OPTIONS, FILES, WARNING CODES, EXIT STATUS, EXAMPLES, LIMITATIONS and SEE ALSO. It is linted by `groff` in CI, and its committed text rendering is diffed so it cannot go stale.
- The manual (`MANUAL.md`) covers both the CLI options and the portal's environment options and scripts.
- Writing the man page found a real inconsistency: the draft said invalid input exits 2, but the code exits 1. The page, the `--help` text and the manual now agree with the code.
